# 皇家生存战 MVP：上线前与上线后检查

## 当前结论

本地可以验证代码语法、数据库脚本的结构一致性、匹配分组逻辑、扣款/退款/奖励的幂等设计、遥测字段、异常记录和离线平衡报告；这些检查不需要发布到生产环境，也不会消耗玩家金币。

本地无法证明真实 Cloudflare 环境中的网络延迟、WebSocket 断线行为、Durable Object 跨请求串行、D1 真实并发、生产密钥权限和真实多人同时入队。这些必须先部署到独立的 staging 环境，用测试账号和测试金币压测；不能用“本地页面能打开”替代。

## 已准备的数据存储

- `arena_matches`：对局规则版本、平衡版本、地图版本、开始/结束、时长、峰值人数、服务器状态/动作计数、异常总数、胜者和结算哈希。
- `arena_match_players`：每名玩家的角色、座位、状态、等级、HP、击杀、伤害、承伤、PvE 击杀、技能次数、状态更新、动作次数、断线/重连次数、排名和出局原因。
- `arena_match_events`：死亡、胜利、主动退出等事件的幂等审计记录。
- `arena_match_telemetry`：每名玩家每 5 秒最多一个样本，记录位置、HP、等级、击杀、伤害、承伤和技能次数；不会按每帧写库。
- `arena_match_incidents`：异常位移、异常 HP/等级/击杀跳变等单独记录，并按去重键避免重复计数。
- `arena_wallet_ledger`：100 金币报名、700 金币胜者奖励和排队退款的流水；幂等键防止重复扣款/发奖。
- `arena_feedback`：第 5 局结束后只出现一次，提交或关闭后不再打扰同一用户。

## 数据库执行顺序

1. 新数据库使用完整的 `cloudflare/data-schema.sql`。
2. 已存在的 D1 数据库先在 staging 执行一次 `cloudflare/migrations/arena-mvp-v2.sql`，确认所有新增列和表存在，再启用 Worker v2。
3. `cloudflare/arena-analytics.sql` 只读，用于汇总对局健康度、角色胜率、异常事件、断线重连、流水和用户反馈。
4. 生产迁移和 Worker 发布必须由负责人单独确认后执行；本次工作不会自动执行。

## 建议的上线门槛

- 先 staging：8 个测试账号同时入队，验证 1 房；再 160 个测试账号验证 20 房分组。
- 验证同一请求重复点击不会重复扣款；排队取消会退款；结算重试不会重复发奖。
- 人为断网后在 45 秒内重连，角色不能无敌；超过 45 秒由服务器判定退出/淘汰。
- 人为制造异常状态，确认只记录 incident，不接受异常位移/复活/计数倒退，并且不影响其他房间。
- 先小流量开放，观察对局时长、异常率、断线率、P50/P99 请求耗时和角色胜率，再扩大流量。

## 仍不能在本地替代的验证

离线 10 万局平衡报告只能说明模拟模型达到当前目标（约 5 次命中击杀、103 个传说角色的胜率分布可接受）；它不能证明真实客户端的服务器权威战斗已经完成。当前 Worker 已有状态校验和审计，但伤害判定仍需要 staging 的真实多人验收，确认客户端技能、碰撞、怪物和毒圈结果与服务器记录一致后，才适合宣称正式上线。
